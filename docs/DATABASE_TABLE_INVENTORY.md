# Physical table consolidation inventory

PostgreSQL migration 222 has 206 physical tables across the public and gross_board_accounting schemas. Migration 225 has 196. The local changes remove seven retired tables and consolidate five active tables into two. The five views remain. The schema migration ledger is included in both counts.

A fivefold reduction would require at most 41 physical tables. The table below assigns each of the 206 originals once, including the seven retirements below the table. It describes a **design exercise** for the remaining 155 net removals. A target family can require several physical tables when its keys, retention or locking differ. Only board presence and provider sync days have passed through active-table migrations here.

## Order of experiments

1. Optimize the queries for an individual board week and driver before combining dispatch storage. Compare financial source routing, historical duplicate claims, transfer reversals and reset balances under simultaneous edits. Slot zero and extra slots are the next plausible consolidation. A replacement must retain the nullable source ID, slot tombstones, revision fencing, all dated crew assignments and existing frozen statement identity.
2. Measure provider operations, snapshots and event pairs separately. Change one provider pair at a time. Exercise partial spool delivery, lost responses, environment isolation, retention and independent row claims. Apply a composite foreign key to each deduplication scope. A shared table needs its own indexes for actionable rows.
3. Test typed fleet assignments, documents and audit families with realistic data volumes. Compare per-query shared buffers, WAL per update, concurrent writes and permission projection. An immutable event table requires independently enforced read scopes and append-only permissions for each former table.
4. Leave canonical financial postings, frozen statement bodies and shared payroll epochs in their present tables until a shadow replay proves equal inputs, amounts, postings, lock scope and idempotency across finalization, reopen, revisions and concurrent saves. Benchmark both cache hits and misses on fleet-scale history. Merging canonical and derived storage in a single relation can amplify vacuum work or cause contention.
5. Stage each successful migration as a separate change with a verified restore, explicit binary compatibility, on-disk row counts and application-role parity tests. Reject a design that needs weaker keys, longer tail latency, broader authorization or wider locks to reach its table-count target.

## Tables with no declared foreign keys

A read-only production catalog check on November 19, 2026 counted 196 physical tables across `public` and `gross_board_accounting`. Of the 63 without outgoing foreign keys, 12 have incoming foreign keys. The other 51 have neither, and a live existence check found rows in all 51. The groups below cover each of those 51 once.

The three historical tables held 340 phone normalization records, one dispatcher pay history row and one payroll storage cutover receipt. Their combined PostgreSQL footprint was 176 KiB including indexes and TOAST. Archiving them would simplify the schema, with little effect on board latency. Four provider progress tables could become one, a net reduction of three physical tables. No table in this inventory was removed by this review.
