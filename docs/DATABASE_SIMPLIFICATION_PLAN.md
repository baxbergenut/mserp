# Clustie database simplification and load reduction

**Implementation plan, November 19, 2026.** Prioritize the multi-second delays users experience and the sustained rise in managed PostgreSQL CPU. Reduce time waiting for a connection and work performed while holding one. Monitor memory and application-host headroom, and retire obsolete storage while preserving current behavior. Start performance changes independently of schema migrations.

## Locally implemented and measured

Migration 222 has 206 physical tables, five views and 256 foreign keys. Local migration 225 has **196 physical tables, five views and 248 foreign keys**. The fivefold target is at most 41 physical tables. The [complete inventory](DATABASE_TABLE_INVENTORY.md) maps all 206 originals to either retirement or a prospective destination. Retaining current behavior and performance takes precedence over that target.

- **223** retires five empty accounting cutover tables, the untouched accounting settings singleton and the empty transfer audit table. An unexpected row, edited singleton, pending payroll capture or dependent view rolls back the migration. Historical capture IDs, dispatched events and revision evidence survive.
- **224** replaces the two active board-presence tables with one. The composite key, typed cell checks, session cascades and separate post-commit channels preserve simultaneous identical client IDs across the boards.
- **225** replaces three provider sync-day tables with one. Completed-day checks retain provider/environment boundaries and timestamps. Empty Relay and PrePass days use one write when complete and zero calls for a partial empty day. Populated days retain the existing transaction and financial guards. PrePass reads the matched truck from the location update, saving one round trip per toll.
- Session authorization now reads categories and overrides in the session query. Status and Gross Board reads batch requests that arrive before a snapshot begins. Status Board also scopes batching by user and administrator status. Plain loads skip trip validation only when the record has no split signal, selected trip, saved allocation or trip evidence. Pinned load IDs use their primary key directly. Number-only plans retain their uniqueness and availability checks. Gross Board balance detail ranks only the requested driver's history.
- The sidebar fetches both authorized counts in a single request for task viewers. Other signed-in users keep their feedback count. Birthday checks avoid writes on ordinary days. Idle driver-service sweeps use one eligibility read. An expense options query includes paid-by users. Reports release their pooled connection before waiting on an in-flight report. SQL, pool wait, hold and worker metrics are recorded without values or user IDs.

### Fleet-size replay

PostgreSQL 17, 120 synthetic trucks, 960 current and 12,000 historical loads from the existing reports scale fixture. Five independently authenticated browser API clients for one administrator opened both boards and their badges in 10 measured bursts. One warm-up was excluded and baseline/candidate order alternated. Each burst does the same visible work.

| Measurement | Migration 222 and original app | Migration 225 and revised app |
| --- | ---: | ---: |
| HTTP requests | 350 | 300 |
| pgx calls | 2,400 | 1,520 |
| Total measured SQL time across requests | 69.48 s | 22.63 s |
| Total measured connection-acquisition wait | 10.44 s | 2.48 s |
| Request median / p95 / p99 | 68 / 970 / 1,026 ms | 69 / 463 / 684 ms |
| Requests taking at least one second | 9 | 0 |

A second replay used five distinct non-administrator dispatch accounts, so Status Board snapshots remained viewer-specific. Over ten bursts, requests fell from 350 to 300, pgx calls from 2,450 to 1,850, SQL time from 59.18 s to 24.85 s and connection wait from 8.33 s to 0.89 s. Median/p95/p99 request times went from 60/803/880 ms to 53/410/481 ms. Both runs had zero requests over a second.

Separate single-connection diagnostics ran five uncached board reads per process against the **same populated schema**. The median PostgreSQL backend CPU time over three alternating trials was 1,188 → 531 ms for Status Board and 1,359 → 969 ms for Gross Board. Median sampled peak working set was 38.8 → 37.2 MiB and 36.7 → 38.6 MiB respectively. Working set includes mapped pages. These observations support lower CPU per board read. Managed database CPU, host memory and VPC impact require a production observation window.

Both boards returned identical serialized results from the two binaries against the same dataset. Driver Pay and Investor Pay summary comparison found only the expected top-level input revision difference when the migration-222 binary inspected migration-225 revision rows. Financial fields matched. Fresh-schema, incremental, concurrency and browser verification exercise writes and reversals separately.

### Browser verification

The board grid, two-board presence, Gross Board multi-user edits and reconnects, sensitive investor access, accounting retirement, and concurrent Driver Pay and Investor Pay finalization checks passed. The longer Status Board browser script passed editing, history and undo, conflict recovery, destination selection and queue reads. It stopped at its legacy expectation that Status Board can remove a Gross Board-owned plan. The original and revised backends reproduced the same failure with the same browser build and fixture. The application directs users to Gross Board to remove that plan. Later steps of that script remain unverified.

## Original investigation and rollout plan

The sections below record the initial hypotheses and the proposed production verification. The migration counts, timings and completed local checks above supersede the original estimates.

### 1. Attribute the spikes

The six-hour PostgreSQL Insights charts supplied on November 19 show CPU around 35% early in the window, a tooltip reading of 44.2% at 07:18:20, and a rising workload after about 08:30. CPU stayed near the chart ceiling around 09:50–10:15 and repeatedly returned there afterward. Memory fluctuated between roughly 63% and 75%, ending near 70%. These are visual estimates except for the tooltip. The operator reports that the VPC is doing well. Prioritize database CPU attribution and keep memory and host metrics as comparison signals.

Compare **05:30–05:55** with **09:50–10:15** in dashboard time, confirming the timezone before matching logs. For each 25-minute window, compare requests and completed jobs per minute, SQL calls and DB milliseconds per request/job, and total DB time by route, worker and query fingerprint. This distinguishes increased traffic from higher cost per action or overlapping background activity. Use historical query insights where available. If only cumulative PostgreSQL counters remain, collect interval deltas during the next recurrence. A useful first result is a ranked list of which workloads added the most DB time during the high-CPU window, with their call counts and per-call costs.

Use existing production telemetry first. Align timestamps for a reported spike, an ordinary busy period, and a quiet period. Include a week rollover, export, sync or backup window when it overlaps a spike. Record release, feature flags, instance count, request mix, concurrent users, worker throughput and monitoring resolution. Historical logs can supply these windows while development proceeds.

### 2. Reduce recurring work first

### Production slow requests on November 19

Two read-only samples of completed requests from the API journal give a starting point. Times here are New York time (UTC−5). The selection excludes route patterns containing `events` or `stream` and uses recorded server durations. The dashboard timezone still needs confirmation before aligning individual CPU samples.

| Five-minute window | Sampled requests | At least 1 second | At least 5 seconds |
| --- | ---: | ---: | ---: |
| 05:30–05:35 | 111 | 0 | 0 |
| 10:00–10:05 | 1,893 | 1,811 | 1,330 |

In the busy sample, **1,694 of the 1,811 requests lasting at least one second** accumulated at least half their elapsed duration in pgx pool acquisition. One successful `GET /driver-pay` took 25.526 seconds with 32 database calls, 20.181 seconds acquiring connections and 5.344 seconds in database calls. A successful `POST /auth/birthday` took 31.084 seconds with four calls, 9.647 seconds acquiring connections and 21.437 seconds in database calls. These timings identify where requests waited. Identifying which transactions occupied the pool requires connection and PostgreSQL wait evidence.

1. **Find the connection holders during a recurrence.** Sample acquired, idle, and maximum pool connections alongside transaction duration, DB wait events, blocking chains and worker activity. Instrument sampled connection hold times by route or job if missing. Check for handlers that acquire another connection while holding an open transaction or result set, repeated SQL within a transaction, and external work performed before release. The current pool configuration is ten connections per process. Test any size change against DB CPU, memory and throughput.
2. **Measure repeated client requests.** The busy window included 223 feedback-count reads, 198 task-count reads, 196 session reads, 439 board-presence reads, and 272 presence updates. Both board snapshot endpoints together used 3,719 pgx calls over 193 requests. Replay the multi-tab and reconnect paths to identify duplicate refreshes, and preserve expiry, permission revocation, and live updates when coalescing work.
3. **Fix the largest measured sources of delay.** For each slow route, compare a typical and a slow instance with the same inputs. Use query fingerprints and plans when time is in SQL, blocking evidence when time is in locks, and connection hold times when pool acquisition dominates. Measure external waits and browser render time where server traces leave a gap. Keep long-lived streams in a separate report measuring first event, delivery lag and reconnects.
4. **Verify tail latency under load.** Reproduce the busy request mix and concurrency, including workers and multi-tab traffic. Compare counts and proportions above one and five seconds, p95/p99, pool wait, SQL time, errors, completed throughput and time to visible browser result. Use matching traffic and data for the before/after comparison. Track the rare slow actions as well as high-volume routes.

Implement and measure each change independently. Prioritize changes that release occupied connections earlier or eliminate repeated acquisitions in the observed busy workload. The following code-level candidates supply the first experiments.

### 4. Ship in independently reversible releases

1. **Observability and replay.** Land the scorecard and representative synthetic scenarios. Establish budgets per route and job, including statement count, round trips, DB time, peak resource pressure and user-visible timing.
2. **Performance releases.** Ship one independently measurable change at a time, beginning with the pool holder or source of repeated requests that accounts for the most peak delay. Compare matched windows after rollout. If savings shift work to workers, Go memory, database sorts or retries, include that cost in the result. Revert a regression independently.
3. **Compatibility release.** Remove runtime dependencies on the selected retired tables while their storage still exists. Test this release against both schema shapes so it is a viable application rollback target. Update the payroll source inventory, revision coverage and recovery tooling together. Exercise fresh bootstrap and an incremental upgrade with representative historical data.
4. **Physical retirement.** Use the next available numbered migration and update `backend/sql/init.sql`. Install the matching deploy helper first, quiesce relevant writers, take and test a fresh backup, recheck the exact row and dependency preconditions under lock, then drop only named objects using restrictive dependency behavior. Abort on any mismatch. Fence rollback to binaries that still require removed objects. Rehearse forward repair and isolated backup restore before cutover. Preserve post-cutover commits when planning any recovery.
5. **Verification.** Start with `TestAccountingCutoverRetiredDatabase`, `TestPayrollCacheSchemaCoverageDatabase`, `TestLoadWeekTransfersDatabase`, `TestPayrollResourceConcurrencyDatabase` and `TestReportsClosedWeekDatabase`. Apply migrations with the migration role and exercise application behavior as `mserp_app`. Run the browser checks for accounting retirement, concurrent finalization, investor permissions and multi-tab boards. Exercise ordinary dispatch edits, duplicate loads, payroll finalize/reopen/retry, external expense settlements, provider recovery and report CSV. Compare normalized API responses, frozen statement contents, ledger sums, recipients and posting counts. Regenerate the ER diagram and compare the physical inventory with the approved removals.

**Completion criteria.** At baseline, agree on numerical CPU headroom and available-memory floors for the actual service sizes. For each performance release, require a repeatable improvement in its targeted resource at equivalent throughput, with browser p95 and queue age within baseline variability. Track regressions in spill/WAL volume, pool waits, host RSS and accounting correctness. Report idle calls, calls per completed action and peak-period measurements after deployment. Every removed table has a verified disposition and recovery path. Every optimized financial path passes parity and concurrency checks. Keep the actual savings and remaining high-cost paths in the release record.
